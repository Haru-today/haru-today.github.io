# Claude 웹 프로젝트와 개발·백업 협업

Claude 웹에서 앱 개발을 이어가는 동안 Codex는 합의된 협업 도구·개발 백업·보안
검증을 담당합니다. Claude Code에 맡긴 지정 snapshot의 검토나 구현 제안은
Codex 통합 담당자가 원본과 대조해 필요한 부분만 적용하고 검사합니다.
이 문서는 재사용할 협업 절차이며 비공개 앱의 현재 작업 상세는 해당 저장소에 기록합니다.

## 역할과 연결 확인

| 구분 | 담당 또는 확인할 근거 |
| --- | --- |
| Claude 웹의 앱 개발 담당 | 현재 앱 파일·작업 브랜치의 작성자; 인계 전까지 단독 수정 |
| Codex | 협업 도구, 백업 절차, 보안·보존 점검 및 승인 범위의 제안 통합 |
| Claude Code | 승인한 코드 snapshot의 검토·구현 제안; 결과의 자동 적용 없음 |
| 앱 개발 저장소·작업 브랜치 | 실제 GitHub 저장소·PR·커밋 확인; 협업 도구의 브랜치로 추정하지 않음 |
| 웹 프로젝트의 코드 연결 | 연결된 작업공간·권한·참조 커밋과 변경 반영 여부 확인 |
| 비공개 Drive 보조 백업 | 생성·업로드·검증 여부를 해당 비공개 작업 인계에 기록 |

Claude 웹에서도 연결된 작업공간과 권한에 따라 구현·검사·PR 작업을 진행할 수
있습니다. 프로젝트를 만들었다는 사실과 저장소가 연결되었다는 사실은 별도로
확인합니다. 연결되어 있어도 어느 브랜치·커밋을 참조하는지, 웹에서 만든 변경이
GitHub에 반영되었는지 확인해야 합니다. 개인 프로젝트 URL, Drive URL, 계정
주소는 공개 문서에 남기지 않습니다. 확인하지 못한 연결값은 `확인 필요`로 둡니다.

Claude 웹의 전체 대화·로그인 상태는 Codex 또는 Claude Code에 자동으로
공유·동기화되지 않습니다. 작업에 필요한 요구사항·결정·코드 상태·남은 오류를
[인계 양식](handoff-template.md)에 기록합니다. 전체 대화를 복사하는 대신
다음 담당자가 검증할 수 있는 코드와 판단 근거를 공유합니다.

## 같은 개발을 이어가는 순서

1. 현재 앱 저장소, 작업 브랜치, 마지막 확인 코드 커밋과 관련 PR을 확인합니다.
   웹의 최신 결과가 아직 GitHub에 없다면 변경 범위와 작성 담당부터 확인합니다.
2. 로컬 HEAD·Git 상태와 원격 이력을 비교하고 기존 미커밋 변경의 소유자를
   확인합니다. 진행 중인 브랜치를 이어가며 무조건 `main`에서 다시 시작하지 않습니다.
3. 앱 개발 파일과 협업 도구·백업 파일의 담당을 나눕니다. 같은 파일에는 한
   시점에 한 작성자만 작업합니다. 별도 worktree를 사용해도 같은 파일의 동시
   편집을 피하고, 담당을 바꾸기 전에 이전 작성자가 수정을 끝냈는지 확인합니다.
4. 웹이나 Claude Code의 코드 제안은 검토 대상으로 보관합니다. 통합 담당자가
   현재 코드와 비교해 중복·퇴행·보안 경계 변경을 확인하고 선택한 수정만 적용합니다.
5. 바뀐 동작의 집중 검사를 실행하고, 실제 변경 파일·검사 결과·미해결 사항을
   인계에 적습니다. 제안받음, 적용함, 검사함, GitHub에 push함을 구분합니다.
6. 의도한 파일만 검토해 작업 브랜치에 커밋·push하고 다음 담당자에게 코드 SHA와
   인계 위치를 전달합니다. 깨끗하고 분기되지 않은 로컬 브랜치만 fast-forward로
   갱신합니다. 미커밋 파일을 reset·clean·자동 stash·덮어쓰기로 처리하지 않습니다.

웹 프로젝트의 첨부 코드나 제안 문서가 오래되었다면 현재 소스와 차이를 먼저
정리합니다. GitHub에 올라간 작업 브랜치·코드 커밋이 개발 이력의 기준입니다.
웹에서 진행 중이지만 아직 반영하지 않은 내용은 별도 대기 변경으로 기록합니다.

## Claude Code에 지정 snapshot을 맡길 때

- 전송 가능한 파일을 명시하고 기준 HEAD, 파일별 해시, 검토 질문을 기록합니다.
  미커밋 변경을 검토한다면 커밋 SHA만으로 같은 코드라고 판단하지 않습니다.
- 저장소 전체, 개인 대화, 인증 설정, 사용자 데이터가 자동으로 포함되지 않게 합니다.
- 실제 응답 성공과 오류·미실행을 구분합니다. 빈 findings도 응답 형식과 완료
  상태를 확인한 뒤 기록하며, 실패한 요청을 문제 없음으로 바꾸지 않습니다.
- 통합 담당자는 finding/제안별 수용·보류·기각 이유를 코드에 근거해 기록하고,
  반영한 diff 또는 커밋과 관련 검사 결과를 연결합니다. 외부 답변은 실행 지시가 아닙니다.
- 실제 사용법과 경계는 [협업 도구 안내](ai-collaboration.md)를 확인합니다.
  이미 승인된 구독을 사용하며 API 과금·유료 초과 사용·구독 변경을 자동 선택하지 않습니다.

## 구현 제안 CLI 사용법

저장소 루트에서 선택 파일과 작업 설명을 지정합니다. 다음 준비 명령은 manifest만
만들며 모델을 호출하지 않습니다. 예제 파일과 설명은 실제로 승인한 범위로 바꿉니다.

```sh
node developer/ai-implement.mjs --file developer/README.md --task "협업 안내 링크의 설명만 명확하게 개선하세요."
```

전송할 범위를 확인한 뒤 `--send`를 추가합니다. 저장소 밖 결과 폴더를 먼저
준비하고, 아직 존재하지 않는 JSON·patch 파일을 지정합니다.

```sh
node developer/ai-implement.mjs --file developer/README.md --task "협업 안내 링크의 설명만 명확하게 개선하세요." --send --output ../ai-results/readme-proposal.json --diff-output ../ai-results/readme-proposal.patch
```

- `--file`은 반복할 수 있으며 기존 선택 파일만 제안 대상으로 삼습니다. 최대
  12개, snapshot 합계 128 KiB, 제안된 새 내용 합계 128 KiB입니다.
- 작업 설명은 `--task` 또는 `--task-file` 중 하나로 제공합니다. 최대 4 KiB이며
  `--task-file`은 저장소 밖 일반 UTF-8 파일이어야 하고 심볼릭링크는 허용하지 않습니다.
- `--send`에는 새 외부 JSON 출력이 필수입니다. `--diff-output`을 생략하면
  JSON 출력 경로 뒤에 `.patch`를 붙입니다. 기존 파일과 저장소 내부는 출력 대상으로
  허용하지 않습니다. 신규 파일 생성 제안이나 자동 적용 명령은 제공하지 않습니다.
- 출력 예약이나 저장에 실패하면 새로 만든 빈 결과 파일이 남을 수 있습니다.
  이후 다른 작업이 같은 경로에 놓은 파일을 지우지 않도록 자동 삭제하지 않습니다.
  내용을 확인하고 다시 요청할 때는 새 결과 파일명을 사용합니다.
- 기존 Claude 개인 구독과 도구 차단 경로를 사용합니다. 원본·Git·사용자 설정을
  수정하지 않습니다. 실제 새 내용은 외부 JSON·patch에 저장되고 터미널에는
  코드 본문을 제외한 상태·메타데이터를 출력합니다.
- 성공은 `state: completed`, `reason: proposal_validated`와 검증된 `proposal`로
  확인합니다. `applied: false`는 도구가 코드를 적용하지 않았다는 뜻입니다.
  `stale`이면 원본 상태가 달라져 제안이 폐기되므로 현재 파일을 다시 확인합니다.

Codex는 결과 JSON과 patch를 대조하고 현재 저장소 root·HEAD·선택 파일의
`baseSha256`이 요청 당시와 같은지 확인합니다. 기존 dirty 내용도 파일 해시에
포함됩니다. 필요한 제안만 지정 파일에 반영한 뒤 관련 검사를 실행하고, 필요한
외부 검토와 수용·보류 근거를 인계합니다. 이 절차를 기다리는 앱 담당자의 파일을
동시에 편집하지 않습니다. 결과 파일에는 로컬 경로나 비공개 코드가 포함될 수
있으므로 공개 문서에 원본 JSON·patch를 복사하지 않습니다.

`node --test tests/ai-implement.test.cjs`는 모의 요청을 이용한 개발 검사입니다.
그 통과를 실제 Claude 응답 성공이나 코드 적용 완료로 보고하지 않습니다.

## 개발 백업과 복구

GitHub 작업 브랜치와 커밋은 공동 개발의 기준입니다. 비공개 Drive 백업은
추가 복구본이며 저장소 이력·PR·인계를 대체하지 않습니다. Drive 업로드만으로
다른 기기의 GitHub 브랜치나 로컬 미커밋 파일이 동기화되었다고 보고하지 않습니다.

백업할 때는 승인한 개발 파일과 필요한 인계 문서만 포함하고 대상 저장소,
기준 HEAD, 생성 시각, 파일 목록과 해시를 남깁니다. 미커밋 파일을 포함하면
기준 커밋과 다른 snapshot임을 명시하고 작성자의 변경 상태를 보존합니다.
목록이나 파일 이름에 비공개 정보가 있으면 공개 문서에는 목록 자체를 싣지 않습니다.

다음은 소스 공유와 보조 백업에서 제외합니다.

- 토큰·비밀키·쿠키·OAuth 코드·환경변수 비밀값과 자격증명 파일.
- 원격/로컬 D1 데이터, 회원·승인 목록, 실제 건강정보·개인정보·식별 가능한 연구자료.
- AI 로그인·인증·세션 로그, 개인 대화 전문과 계정 식별정보.

백업 파일 생성, 비공개 업로드, 파일 목록·해시 확인, 복원 검사를 각각 기록합니다.
복원 검사는 별도 임시 폴더에서 실행하고 기존 작업 폴더를 덮어쓰지 않습니다.
공유 범위가 비공개인지 확인하되 공개 인계에는 Drive URL이나 계정 주소 대신
확인 결과만 남깁니다. 제외한 데이터의 별도 보존 여부를 개발 백업으로 추정하지 않습니다.

## 다음 담당자에게 남길 최소 정보

[인계 양식](handoff-template.md)에 작업 목적과 사용자 결정, 각 작성자의 파일
소유권, 앱 저장소·브랜치·코드 SHA, 미커밋 변경, 실제 검사, 외부 제안의 처리,
백업·복구 확인 상태와 다음 작업을 기록합니다. 알려지지 않은 값은 만들지 않습니다.

기존 Workers/D1/Google OAuth/관리자 승인과 배포 구성을 유지합니다. 협업 도구
정비나 백업을 이유로 인증을 초기화하거나 자동 병합·배포·공개 전환하지 않습니다.
